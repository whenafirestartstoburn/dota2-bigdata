# Конвенции монорепозитория

## Структура и скоуп

Код живёт в `packages/*` (`workspaces.packages` корневого `package.json`).
Скоуп пакетов зафиксирован как `@app` — публикации в npm нет, подставлять
своё имя незачем: пакет всегда называется `@app/<имя>` (`@app/shared`,
`@app/api` и так далее).

`packages/shared` — общий код: env, подключения к инфраструктуре, утилиты.
Его барель — `packages/shared/src/app.ts`, `package.json` пакета указывает на
него полем `"main"`. Внутри барель реэкспортирует относительными путями
(`export * from './utils/db'`), а не через имя пакета — самоссылка на
собственный `@app/...` не нужна и не встречается нигде в шаблоне.

## Алиасы

Внутри пакета импорт идёт по алиасу `#src/...`. Он объявлен не в
`tsconfig.json`, а полем `"imports"` в `package.json` самого пакета, и
значение обязано нести расширение файла:

```json
{
	"imports": { "#src/*": "./src/*.ts" }
}
```

Причина — не стиль, а работоспособность. Если положить `#src/*` в `paths`
`tsconfig.json`, `tsc` резолвит `paths` для **всех** файлов программы, включая
чужие исходники, втянутые через `@app/*`. Как только пакет `api` импортирует
`@app/shared`, `tsc` начинает резолвить `#src/*` внутри исходников `shared`
относительно конфига `api` — и второй пакет падает с `TS2307`. Прогон
прототипа воспроизвёл эту ошибку буквально. `imports` в `package.json`
устроен иначе: поле принадлежит самому пакету, поэтому алиас резолвится
одинаково и когда его читает `tsc` чужого пакета, и когда его резолвит Bun в
рантайме — чужие исходники не задеваются. Отсюда правило: **в пакетном
`tsconfig.json` `paths` не появляется никогда**, алиас — только через
`package.json`.

Между пакетами импорт идёт по имени: `@app/shared` гарантирован — `core`
всегда несёт пакет `shared`, — а для остальных пакетов схема та же,
`@app/<имя>`, если такой пакет в проекте есть. Зависимость объявляется в
`dependencies` через `workspace:*`:

```json
{
	"dependencies": { "@app/shared": "workspace:*" }
}
```

Импорт из `shared` возможен двумя способами: через барель (`import { sql }
from '@app/shared'`) и напрямую по пути (`import env from
'@app/shared/src/utils/env'`), когда нужен один символ, а не весь барель со
всеми его побочными эффектами верхнего уровня.

## Версии

Диапазон версии живёт ровно один раз — в `workspaces.catalog` корневого
`package.json`. Пакет не пишет диапазон сам, он ссылается на каталог:

```json
{ "dependencies": { "zod": "catalog:" } }
```

Это не вкусовщина. Если диапазон продублировать в `package.json` пакета,
`bun install` может положить два экземпляра одной библиотеки в
`node_modules` — и тогда `instanceof ZodType` внутри oRPC начинает
возвращать `false` для схем, пришедших из другого экземпляра `zod`, хотя
код выглядит корректным. `catalog:` устраняет саму возможность разъезда:
второй копии просто неоткуда взяться.

## tsconfig

Пакетный `tsconfig.json` состоит из двух полей и ничего больше:

```json
{ "extends": "../../tsconfig.json", "include": ["src"] }
```

Все флаги компилятора живут в одном корневом файле; пакетный только
наследует его и указывает свой `include`. Среди унаследованных флагов —
`strict` (база, без которой остальные проверки бессмысленны) и
`noUnusedLocals` (неиспользованный импорт или переменная — не
предупреждение, а ошибка `tsc`, останавливающая `typecheck`). Ещё два флага
меняют то, как пишется код, сильнее остальных:

- `noUncheckedIndexedAccess` — обращение по индексу возвращает `T |
  undefined`, а не `T`. `arr[0]` типизируется как `T | undefined`, и до
  использования значение нужно проверить или подстраховать:

  ```ts
  const first = arr[0]
  if (!first) throw new Error('пусто')
  // либо
  const value = arr[0] ?? fallback
  ```

- `verbatimModuleSyntax` — импорт типа обязан быть помечен `import type`,
  иначе ошибка компиляции. Смешанный импорт значения и типа из одного
  модуля разделяется явно: `import { readFile, type Dirent } from
  'node:fs'`.

## biome

Форматирование: одинарные кавычки, точки с запятой `asNeeded` (только где
без них код развалится), `lineWidth` 80, отступ — табы.

Рантайм — Bun. Задержки, файлы, процессы, хеши — встроенные `Bun.sleep`,
`Bun.file` / `Bun.write`, `Bun.spawn`, `Bun.CryptoHasher`. Не оборачивать
их в хелпер проекта. Подробности — скилл `bun-builtins`.

Доменный async — `async`/`await` и `Promise`. Не тащить Effect, neverthrow
и другие Result-рантаймы. Ретраи — цикл + `await Bun.sleep`. Ошибки —
классы `Error` и `throw`.

`noDefaultExport` выключен — потому что хендлеры oRPC (блок `api`) сами
являются default-экспортами; запрещать default экспорт значило бы держать
линтер вечно красным на чужом коде.

Сортировка импортов включена принудительно ключом
`assist.actions.source.organizeImports`, кроме файлов, у которых первой
строкой стоит маркер:

```ts
// biome-ignore-all assist/source/organizeImports: ...
```

Путь в конфиге и текст маркера в комментарии — разные формы одного и того
же правила, а не опечатка:

- в `biome.json` — точки, с `actions`: `assist.actions.source.organizeImports`;
- в `biome-ignore` — слэши, без `actions`: `assist/source/organizeImports`.

Маркер стоит на файлах с регионом `<template:imports>`, который собирает
генератор при сборке проекта: если его снять, форматтер при следующем
запуске разберёт регион как обычный код, вынесет из него импорты
генератора и затащит внутрь те, что дописаны руками, — а следующая сборка
сотрёт их, как будто это её собственное содержимое.

## Env

Схема окружения двухуровневая. Общее — в `packages/shared/src/utils/env.ts`
(`baseEnv`); это гарантированный файл, он приезжает с блоком `core`
независимо от того, что ещё выбрано в проект. Переменные, нужные только
одному пакету, — в собственном `src/utils/env.ts` этого пакета, через
`baseEnv.extend({...})`, если у пакета вообще есть свой env. Один `.env`,
лежит в корне монорепозитория — отдельного файла на пакет не заводится.

Список переменных генератор собирает вокруг маркеров внутри `z.object({...})`:

```ts
export const baseEnv = z.object({
	// <template:baseEnv>
	NODE_ENV: z.enum(['development', 'production']),
	// </template:baseEnv>
})
```

Тот же приём — пара комментариев вокруг тела `z.object` — используется и
там, где список собирают несколько блоков сразу. Это касается файлов с
регионом: то, что дописано внутри маркеров, генератор перетирает при
следующей сборке — туда пишут блоки, — а то, что дописано вне маркеров, не
трогает. У файлов без регионов, которые генератор рендерит целиком —
корневой и пакетный `package.json`, `tsconfig.json` пакета, — такой защиты
нет: они пересобираются заново при каждой сборке независимо от того, что в
них дописано руками. Подробнее об этом — в разделе «Новый пакет».

## Новый пакет

Пакет заводится командой шаблона:

```sh
template package <имя> --kind service|lib|scripts
```

| kind | Что получает |
|---|---|
| `service` | `src/app.ts` с graceful shutdown, свой `src/utils/env.ts`, скрипт запуска в корневом `package.json` |
| `lib` | только экспорты: `src/app.ts` как барель, `main` указывает на него |
| `scripts` | папка одноразовых скриптов; точки входа нет, запускаются по пути |

Команда пишет `package.json` пакета (поле `imports` с алиасом `#src/*` и
`workspace:*`-зависимости), `tsconfig.json` с `extends` на корневой конфиг,
строку `tsc -p packages/<имя>` в корневом скрипте `typecheck` и строку в
таблице «Структура» в `CLAUDE.md` проекта.

Содержимое исходников после этого — дело человека: заготовка (`src/app.ts`
у `lib`, `src/example.ts` у `scripts`) кладётся ровно один раз, чтобы `tsc`
не падал `TS18003` на пустом `src/`, и пересборка её больше не трогает —
написанное в этих файлах переживает и `template add`, и повторный
`template package`.

С манифестами пакета иначе, и об этом лучше знать заранее. `package.json` и
`tsconfig.json` пакета — файлы **без маркерных регионов**: генератор
пересобирает их целиком при каждой сборке. Зависимость, дописанная руками в
`packages/<имя>/package.json`, исчезнет; флаг, дописанный в пакетный
`tsconfig.json`, — тоже. Флагам место в корневом `tsconfig.json`: оттуда их
наследует каждый пакет, и правка переживает сборку. А зависимости пакету,
созданному командой, генератор пишет сам и только вычисленные
(`@app/shared`, сервису ещё `zod`) — дописать свою так, чтобы она пережила
пересборку, сегодня негде: у такого пакета нет блока, который бы её объявил.

То же и с корневым `package.json`, и это цена ручного пути: генератор
пересобирает его целиком по списку **известных ему** пакетов. Пакет,
заведённый руками, а не командой, генератору неизвестен, поэтому дописанная
в `typecheck` строка исчезнет при первой же пересборке. Чтобы этого не
случилось, пакет дописывается в `extraPackages` в `template.json` — именно
оттуда команда и берёт список пакетов, которых не приносит ни один блок.

Имя пакета — строчные буквы, цифры и дефис, первый символ не дефис. Имя,
которое приносит какой-нибудь блок шаблона, команда отвергает и называет
этот блок в отказе: у пакета из блока свои точки сборки, поэтому получать
его нужно установкой блока, а не заводить руками под тем же именем.

Точка входа пакета — всегда `src/app.ts`, как у `shared` и у любого другого
пакета в шаблоне; `index.ts` и `main.ts` не используются нигде.
